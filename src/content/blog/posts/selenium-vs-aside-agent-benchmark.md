에이전트에게 웹 검수를 시킬 때 저는 보통 Selenium을 붙여 줍니다. 그러다 [aside](https://aside.com/)라는 AI 브라우저를 쓰게 됐는데, 애초에 에이전트용으로 만든 브라우저라면 검수도 더 잘하지 않을까 하는 생각이 들었습니다.

비교한 자료가 있나 찾아봤지만 마땅한 게 없었습니다. aside가 공개한 [벤치마크](https://github.com/at-inc/aside-benchmarks)는 웹 작업을 얼마나 끝까지 해내는지를 잰 것이고, 웹 테스트 쪽 벤치마크인 [WebTestBench](https://arxiv.org/html/2603.25226v1)는 Playwright만 썼습니다. 그래서 직접 재 보기로 했습니다.

결론부터 말씀드리면 검수와 자동화는 Selenium이 나았고, 봇 차단이 걸린 사이트에서는 aside가 압도적이었습니다.

## 어떻게 쟀나

검수 능력을 재려면 정답이 있어야 해서, 버그를 일부러 심은 사이트를 세 개 만들었습니다. 결함 27개를 심은 쇼핑몰, 캐러셀이나 토스트처럼 움직이는 요소가 많은 랜딩·대시보드(결함 16개), 그리고 자동화 작업 12개를 넣은 사내 포털입니다. 사내 포털에는 Shadow DOM, 다른 출처 iframe, 드래그앤드롭, 브라우저 기본 확인 창, 팝업 로그인, 파일 업로드·다운로드처럼 자동화하기 까다로운 것들을 골라 넣었습니다.

에이전트는 Claude Code 서브에이전트(Claude Opus 5.5)를 썼고, 같은 프롬프트에 도구 설명만 바꿔서 돌렸습니다. aside는 Playwright와 비슷한 스크립트로 브라우저를 직접 조종하는 `aside repl`을 썼습니다. 판단은 같은 모델이 하고 손만 바꿔야 비교가 된다고 봤기 때문입니다.

채점은 결과에서 도구 이름을 지운 뒤 다른 에이전트에게 정답지와 대조하게 했습니다. 자동화 작업은 성공했는지를 서버가 직접 기록하게 했습니다.

## 일반 검수는 싱겁게 무승부

첫 라운드는 싱겁게 끝났습니다. 쇼핑몰 결함 27개를 Selenium도 aside도 세 번 모두 다 찾았고, 오탐도 없었습니다. 걸린 시간(약 15분)과 토큰도 비슷했습니다.

로그를 보니 aside 쪽 에이전트는 빈 기능을 다 돌아서 가고 있었습니다. 콘솔 에러를 받을 수 없으니 페이지에 직접 훅을 심었고, 화면 크기를 바꿀 수 없으니 375px짜리 iframe을 띄워서 모바일 화면을 확인했습니다. Opus 정도면 도구가 좀 불편해도 결과는 맞춘다는 얘기입니다.

그래서 모델을 Haiku 4.5로 낮춰 봤고, 여기서 차이가 났습니다. Selenium 쪽은 결함의 14%를, aside 쪽은 7%를 찾았습니다. 토큰은 aside가 세 배 넘게 썼습니다(0.82M 대 2.80M). aside 쪽 Haiku는 "헤더 링크가 하나도 동작하지 않는다", "모바일 화면을 테스트할 수 없다" 같은 내용을 사이트 결함이라고 보고했는데, 확인해 보니 전부 도구 쪽 문제였습니다.

aside의 장점으로 꼽히는 스냅샷도 검수에서는 거의 쓰이지 않았습니다. 페이지를 접근성 트리로 압축해 보여 주는 기능인데, 실제 Wikipedia 문서로 재 보면 HTML이 61만 자일 때 스냅샷은 4.9만 자라 확실히 가볍습니다. 그런데 에이전트들은 스냅샷을 실행당 두세 번만 보고, 나머지는 페이지에 JavaScript를 넣어 DOM을 직접 뒤졌습니다. Selenium 쪽 에이전트도 똑같이 했습니다. 검수에서는 결국 두 도구 모두 JS를 넣는 통로로만 쓰였습니다.

## 움직이는 화면에서는 aside가 반대로 보고했다

애니메이션이 많은 화면에서는 두 번씩 돌려서 Selenium이 16개를 모두, aside가 14개를 찾았습니다.

가장 아쉬웠던 건 설정 저장 버그입니다. 저장 요청은 서버에서 500으로 실패하는데, 화면에는 "Saved ✓"가 그대로 뜨고 에러 토스트는 1.2초 만에 사라집니다. aside는 네트워크 응답을 볼 방법이 없어서 두 번 다 "저장이 잘 된다"고 보고했습니다. 놓친 정도가 아니라 정반대로 보고한 겁니다. Selenium은 브라우저 로그에서 500을 바로 잡았습니다.

## 자동화는 Selenium이 두 배 넘게 빨랐다

사내 포털 작업 12개는 Selenium이 두 번 모두 12개를 약 10분 만에 끝냈습니다. aside는 11개를 해냈고 약 27분이 걸렸으며, 토큰도 두 배 넘게 썼습니다.

aside가 못 한 건 사용자 삭제였습니다. 삭제 버튼을 누르면 브라우저 기본 확인 창이 뜨는데, aside가 이 창을 알아서 닫아 버리고 수락할 방법이 없었습니다. 시간이 오래 걸린 건 `aside repl`이 호출할 때마다 새 세션을 열고, 끝나면 탭을 닫아 버리기 때문입니다. 에이전트들은 결국 파이프로 세션을 붙잡아 두는 우회책까지 직접 만들어 썼습니다.

의외였던 건 closed Shadow DOM입니다. 접근성 트리를 쓰는 aside 스냅샷이라면 안쪽 입력창도 보일 줄 알았는데 보이지 않았습니다. 결국 스크린샷을 보고 좌표로 클릭했습니다. 반대로 다른 출처 iframe, 팝업 로그인, 드래그앤드롭, 파일 업로드·다운로드, 캔버스 서명은 aside도 무리 없이 해냈습니다.

## 봇 차단에서는 aside가 압승

봇 탐지를 시험해 보라고 공개된 페이지들을 한 번씩 방문해 봤습니다. 실제 서비스를 상대로 우회를 시도하거나 CAPTCHA를 푸는 건 하지 않았습니다.

| 테스트 | Selenium headless | Selenium 일반 창 | aside |
| --- | --- | --- | --- |
| [sannysoft](https://bot.sannysoft.com/) 지문 검사 31개 | 4개 실패 | 1개 실패 | 모두 통과 |
| [BrowserScan](https://www.browserscan.net/bot-detection) 판정 | Robot | Robot | Normal |
| [CreepJS](https://abrahamjuliot.github.io/creepjs/) headless 지수 | 100% | 33% | 0% |
| [Cloudflare 챌린지 연습 페이지](https://www.scrapingcourse.com/cloudflare-challenge) | 차단 | 차단 | 통과 |
| [안티봇 챌린지 연습 페이지](https://www.scrapingcourse.com/antibot-challenge) | 차단 | 차단 | 통과 |
| [reCAPTCHA v2 데모](https://www.google.com/recaptcha/api2/demo) 체크박스 | 이미지 챌린지 | 이미지 챌린지 | 바로 통과 |
| reCAPTCHA v3 점수 | 0.9 | 0.9 | 0.9 |

*aside: 체크박스를 누르자 바로 통과했습니다.*

![](/blog/selenium-vs-aside-agent-benchmark/selenium-vs-aside-recaptcha-selenium.png)

*Selenium: 같은 곳을 누르자 이미지 챌린지가 떴고, 여기서 멈췄습니다.*

같은 컴퓨터, 같은 IP였는데도 결과가 갈렸습니다. 차이를 만든 건 IP가 아니라 브라우저 지문과 자동화 흔적, 그리고 aside가 그대로 쓰는 실제 사용자 프로필입니다.

다만 공개 테스트 페이지에서 나온 결과라, 실제 서비스의 엔터프라이즈 봇 차단이나 대량 요청까지 통과한다는 뜻은 아닙니다. 그리고 aside는 가려진 요소를 클릭할 때 실제 클릭 대신 스크립트 클릭으로 바꿔 누르는데, 이런 클릭은 행동 기반 탐지에 걸릴 수 있습니다.

## 정리

| 실험 | Selenium | aside |
| --- | --- | --- |
| 일반 검수 (Opus) | 27/27 | 27/27 |
| 일반 검수 (Haiku) | 14% | 7% |
| 움직이는 화면 검수 | 16/16 | 14/16 |
| 자동화 작업 12개 | 12/12, 약 10분 | 11/12, 약 27분 |
| 봇 탐지 테스트 | 대부분 걸림 | 모두 통과 |

aside는 로그인된 사이트에서 일을 끝내려고 만든 브라우저라서, 검수에 필요한 기능이 몇 가지 빠져 있습니다. 콘솔·네트워크 이벤트를 받을 수 없고, 화면 크기를 바꿀 수 없고, 확인 창도 처리하지 못합니다(2026년 10월, aside CLI 1.26.916 기준). 가려진 버튼도 그냥 눌러 버리니 "오버레이가 버튼을 막는" 버그도 놓치기 쉽습니다. 대신 실제 사용자 프로필로 움직이니 봇 차단은 쉽게 통과합니다. 검수할 때 단점이던 부분이 봇 차단 앞에서는 장점이 된 겁니다.

그래서 저는 나눠 쓰려고 합니다. 검수나 CI 자동화는 Selenium(아니면 Playwright)으로 하고, 봇 차단이 걸린 사이트나 로그인 세션이 꼭 필요한 작업만 aside에 맡길 생각입니다.

직접 만든 작은 사이트에서 조건마다 두세 번씩만 돌린 결과라 일반화하기에는 한계가 있습니다. 중간에 인터넷이 끊겨 에이전트 몇 개가 죽는 바람에 일부는 다시 돌리기도 했습니다. aside 자체 에이전트에게 통째로 맡기는 `aside exec`와 Playwright는 아직 재지 못했는데, 같은 사이트로 이어서 재 볼 생각입니다.
