AI 에이전트에게 웹 검수를 맡길 때는 보통 Selenium 같은 자동화 도구를 쥐여 줍니다. 그런데 요즘은 [aside](https://aside.com/) 같은 AI 브라우저도 나와 있어서, "에이전트용으로 만든 브라우저가 검수에도 더 낫지 않을까?" 하는 의문이 들었습니다. 찾아보니 둘을 검수 용도로 비교한 자료가 없어서 직접 측정해 봤습니다.

> [!abstract] 한눈에 보기
> - **일반 검수**: 강한 모델(Claude Opus 5.5)에서는 둘 다 결함 27개를 모두 찾았습니다. 약한 모델(Claude Haiku 4.5)에서는 Selenium 14%, aside 7%였습니다.
> - **애니메이션 화면 검수**: Selenium 16/16, aside 14/16이었습니다.
> - **자동화 작업 12개**: Selenium은 12/12를 약 10분에, aside는 11/12를 약 27분에 끝냈습니다. aside는 토큰도 2배를 썼습니다.
> - **봇 차단**: Cloudflare 챌린지와 reCAPTCHA v2는 aside만 통과했습니다.
> - **결론**: 검수와 자동화는 Selenium, 봇 차단이나 로그인 세션이 필요한 작업은 aside가 맞았습니다.

## 무엇을 비교했나

- **Selenium**: 에이전트가 Python 스크립트를 작성해 headless Chrome을 조종합니다.
- **aside**: 로그인된 사이트에서 작업을 대신 처리해 주는 AI 브라우저입니다. 사용 방법은 두 가지입니다.
  - `aside exec`: aside 자체 에이전트에게 작업을 통째로 맡깁니다.
  - `aside repl`: Playwright와 비슷한 JavaScript로 브라우저를 직접 조종합니다.

이번에는 `aside repl`을 비교했습니다. 판단은 같은 모델(Claude Code 서브에이전트)이 하고 손에 쥐는 도구만 달라야 공정하다고 봤기 때문입니다. `aside exec`는 연결된 계정의 사용 한도에 걸려 이번에는 측정하지 못했습니다.

## 기존 벤치마크는 없었습니다

- aside가 공개한 [벤치마크](https://github.com/at-inc/aside-benchmarks)는 웹 작업 완수율(Online-Mind2Web 등)입니다. 회사가 직접 측정한 수치이고, Selenium과의 비교는 없습니다.
- 웹 테스트 에이전트 벤치마크인 [WebTestBench](https://arxiv.org/html/2603.25226v1)는 Playwright MCP만 사용했습니다.

검수 용도로 두 도구를 나란히 놓고 측정한 자료는 찾지 못했습니다.

## 실험 설계

정답을 미리 아는 테스트 사이트 3개를 직접 만들었습니다.

| 사이트 | 용도 | 정답 |
| --- | --- | --- |
| Brewly (쇼핑몰, 9페이지) | 일반 검수 | 결함 27개: 기능, 내용, 접근성, 런타임 에러, 화면, 보안 |
| Pulse (랜딩 + 대시보드) | 애니메이션 화면 검수 | 결함 16개: 캐러셀, 깜빡임, 토스트, 스켈레톤, 레이아웃 시프트 등 |
| Opsdesk (사내 포털) | 자동화 | 작업 12개: Shadow DOM, 다른 출처 iframe, 드래그앤드롭, 네이티브 다이얼로그, 팝업, 업로드·다운로드 등 |

공정한 비교를 위해 다음과 같이 진행했습니다.

- 같은 모델에 같은 프롬프트를 주고, 도구 설명만 바꿨습니다.
- 실행마다 포트를 달리해 브라우저 저장소가 서로 섞이지 않게 했습니다.
- 브라우저 밖의 HTTP 도구(curl 등)는 금지했고, 서버 로그로 위반 여부를 확인했습니다.
- 심어 둔 결함이 실제로 재현되는지 검증 스크립트로 먼저 확인했습니다.
- 검수 결과는 익명화하고 도구 이름을 지운 뒤, 별도 에이전트가 정답지와 대조해 블라인드로 채점했습니다. 자동화 작업은 서버가 성공 여부를 직접 판정했습니다.
- 봇 탐지는 에이전트 없이 스크립트로, 공개된 봇 탐지 테스트 전용 페이지에서만 한 번씩 측정했습니다.

## 결과 1: 일반 검수

| 모델 | 항목 | Selenium | aside |
| --- | --- | --- | --- |
| Opus 5.5 (각 3회) | 찾은 결함 | 27/27, 3회 모두 | 27/27, 3회 모두 |
| | 오탐 | 0 | 0 |
| | 시간 · 토큰 | 14.6분 · 3.17M | 15.1분 · 3.50M |
| Haiku 4.5 (각 3회) | 탐지율 | 14% (11~19%) | 7% (4~15%) |
| | 정밀도 | 53% | 43% |
| | 토큰 · 도구 호출 | 0.82M · 14~22회 | 2.80M · 43~59회 |

Opus에서는 차이가 나지 않았습니다. Opus가 aside에 없는 기능을 모두 우회해서 메웠기 때문입니다.

모델이 약해지자 차이가 드러났습니다. aside 쪽 Haiku는 호출할 때마다 끊기는 세션과 빠진 API 사이에서 헤맸습니다. 그러다 "링크가 하나도 동작하지 않는다", "뷰포트를 바꿀 수 없다"처럼 도구의 한계를 사이트 결함으로 보고하기도 했습니다. Selenium 쪽 Haiku는 콘솔 로그와 HTML 소스만으로 보이는 결함(JS 에러, 깨진 이미지, alt 누락)을 매번 찾아냈습니다.

흥미로운 점도 있었습니다. aside의 장점은 페이지를 접근성 트리로 압축해 보여 주는 스냅샷입니다. 실제 Wikipedia 문서로 측정해 보니 HTML 원문이 61만 자일 때 스냅샷은 4.9만 자였습니다. 그런데 검수에서는 이 스냅샷을 거의 쓰지 않았습니다. aside 쪽 에이전트는 실행당 스냅샷을 2~4번 호출한 반면, 페이지에 JS를 넣어 DOM을 직접 조회하는 호출은 55~102번이었습니다. Selenium 쪽도 JS 실행이 56~70번이었습니다. 검수라는 작업에서는 두 도구 모두 결국 "페이지에 JS를 넣는 통로"로 쓰인 셈입니다.

## 결과 2: 애니메이션 화면 검수

| Opus 5.5 (각 2회) | Selenium | aside |
| --- | --- | --- |
| 찾은 결함 | 16/16, 16/16 | 14/16, 14/16 |
| 정반대로 보고한 것 | 0 | 각 1건 |
| 토큰 | 1.5~1.7M | 3.5M |

> [!warning] aside가 두 번 모두 놓친 결함
> 설정 저장 요청은 서버에서 500으로 실패하는데, 화면에는 "Saved ✓"가 그대로 표시되는 결함입니다. 에러 토스트는 1.2초 만에 사라집니다. aside는 네트워크 응답을 볼 수 없어서 두 번 모두 "저장이 잘 된다"는 정반대 결론을 냈습니다. Selenium은 브라우저 로그에서 500을 바로 잡아냈습니다.

깜빡임(초당 5회), 캐러셀 표시 어긋남, 무한스크롤 중단, 멈춘 스피너, 반투명하게 멈춘 모달은 aside도 우회해서 모두 찾았습니다. 모션 줄이기 설정(`prefers-reduced-motion`)을 무시하는 결함은 확인 방법이 갈렸습니다. Selenium은 설정을 직접 에뮬레이션해 확인했고, aside는 에뮬레이션 기능이 없어서 CSS를 읽고 판단했습니다.

## 결과 3: 자동화

| Opus 5.5 (각 2회) | Selenium | aside |
| --- | --- | --- |
| 성공 (서버 판정) | 12/12, 12/12 | 11/12, 11/12 |
| 걸린 시간 | 약 10~11분 | 약 27분 |
| 토큰 · 도구 호출 | 3.3~3.6M · 44~45회 | 7.1~7.5M · 79~89회 |

- **aside가 막힌 작업**: 네이티브 `confirm`·`prompt` 창이 뜨는 사용자 삭제였습니다. aside가 이 창을 자체적으로 닫아 버리고, 수락할 수 있는 API가 없습니다.
- **예상과 달랐던 점**: closed Shadow DOM 안의 폼은 aside 스냅샷에도 보이지 않았습니다. 그래서 스크린샷 좌표로 클릭해 처리했습니다. Selenium도 한 번은 `shadow_root`로 접근했지만 입력이 먹히지 않아 키보드로 입력했고, 다른 한 번은 요소를 찾지 못해 좌표 클릭과 키보드로 처리했습니다.
- **aside가 잘한 것**: 다른 출처 iframe 결제, OAuth 팝업, 드래그앤드롭, 업로드·다운로드, 호버 메뉴, 캔버스 서명(실제 마우스 입력만 인정)은 문제없이 처리했습니다.

시간과 토큰이 두 배 넘게 든 원인은 세션 구조였습니다. `aside repl`은 호출할 때마다 임시 세션이 열리고, 호출이 끝나면 열었던 탭이 닫힙니다. 그래서 에이전트들이 파이프로 REPL 세션을 유지하는 우회 방법까지 직접 만들어야 했습니다.

*aside: 체크박스를 한 번 누르자 바로 통과했습니다.*

*Selenium(일반 창): 같은 위치를 누르자 이미지 챌린지가 떴습니다. 여기서 멈추고 풀지 않았습니다.*

세 경우 모두 같은 컴퓨터, 같은 IP였는데도 결과가 갈렸습니다. 차이는 IP가 아니라 실제 브라우저 지문, 자동화 흔적이 없다는 점, 그리고 사용자 프로필에서 나왔습니다.

> [!note] 이번에 측정하지 않은 것
> - 공개 테스트 페이지에 한 번씩 방문한 결과입니다. 실제 서비스의 엔터프라이즈 봇 차단(Akamai, DataDome 등)이나 대량 요청에 대한 차단은 측정하지 않았습니다.
> - 이미지 CAPTCHA를 푸는 것은 시도하지 않았습니다. `aside repl`에는 CAPTCHA를 푸는 API도 노출되어 있지 않습니다.
> - aside의 클릭은 가려진 요소를 누를 때 합성 이벤트로 바뀝니다. 이런 클릭은 실제 사용자 입력이 아닌 것으로 표시되어, 행동 기반 탐지에는 걸릴 수 있습니다.

## 왜 이런 차이가 났나

aside는 로그인된 사이트에서 작업을 끝내도록 만든 에이전트용 브라우저입니다. QA 계측 도구로 만든 것이 아니어서 검수에 필요한 기능 몇 가지가 빠져 있었습니다. 아래는 2026년 10월 1일, aside CLI 1.26.916 기준입니다.

- 호출할 때마다 임시 세션이 열리고, 끝나면 탭이 닫힙니다. localStorage와 쿠키만 남습니다.
- `page.on('console')`이나 `page.on('response')`를 등록해도 이벤트가 오지 않습니다. 로딩 중에 발생하는 JS 에러나 실패한 요청을 바로 확인할 수 없습니다.
- 뷰포트 크기를 바꾸거나 미디어 설정을 에뮬레이션하는 기능이 없습니다.
- `locator.click()`은 요소가 가려져 있지 않으면 실제 클릭을 보냅니다. 가려져 있으면 에러 없이 합성 클릭으로 바꿔 눌러 버립니다. 자동화에는 편리하지만 "투명 오버레이가 버튼을 막는" 버그를 숨깁니다.
- 네이티브 다이얼로그를 aside가 자체적으로 처리하고, 수락하는 API가 없습니다.
- 사용자의 실제 브라우저 프로필을 그대로 사용합니다. 그래서 다음과 같은 일이 생깁니다.
  - 로그인 폼을 제출하면 aside의 비밀번호 저장 팝업이 검수 대상 페이지에 끼어듭니다.
  - 같은 localhost에서 실행 중인 다른 앱의 쿠키가 보입니다.
  - 다운로드한 파일이 실제 다운로드 폴더에 쌓입니다.

반대로 이 실제 프로필 덕분에 봇 차단은 쉽게 통과했습니다. 같은 특성이 검수에서는 약점, 접근에서는 강점이 된 셈입니다.

## 그래서 언제 무엇을 쓸까

- **검수·QA·CI 자동화**: Selenium이 적합했습니다. 콘솔·네트워크·뷰포트·다이얼로그를 모두 다룰 수 있고, 실행끼리 격리되며, 병렬로 돌릴 수 있습니다. Playwright도 좋은 후보지만 이번에는 측정하지 않았습니다.
- **봇 차단 사이트나 로그인 세션이 필요한 작업**: aside가 적합했습니다.
- **함께 쓰기**: 접근은 aside로, 검증은 Selenium으로 나누는 조합이 현실적입니다. aside로 검수해야 한다면 클릭은 `page.mouse.click`으로 하고, 네트워크 실패는 따로 확인하는 것이 좋습니다.

## 한계

- 직접 만든 작은 사이트에서 조건마다 2~3번씩만 실행했습니다.
- 2026년 10월 1일 기준 버전(aside CLI 1.26.916, Chrome 154, Selenium 4.36)입니다. 두 도구 모두 업데이트되면 결과가 달라질 수 있습니다.
- 토큰 수치는 대부분 캐시 읽기여서, 실제 비용 차이는 표보다 작을 수 있습니다.
- 실험 도중 네트워크 장애로 애니메이션 라운드 3회를 다시 실행했습니다. 장애를 거친 aside 실행 1회는 시간·토큰 비교에서 제외했습니다.
- 에이전트 실행 2회가 서버 동작 여부를 확인하려고 curl을 한 번씩 사용해 규칙을 어겼습니다. 결과에는 영향이 없었습니다.
- `aside exec`(aside 자체 에이전트에게 맡기는 방식)와 Playwright는 아직 측정하지 않았습니다. 같은 사이트로 이어서 측정할 계획입니다.
